    8. Autenticação e autorização

    Duas perguntas distintas se colocam a cada requisição:

    • Quem é o usuário? Isso é a autenticação: o usuário se identificou com um nome de usuário e uma senha, e cada requisição seguinte deve provar que vem dele;
    • Ele tem permissão para acessar esta página? Isso é a autorização: no estudo de caso, somente um usuário com o papel ADMIN gerencia médicos e clientes.

    A prova de identidade deve acompanhar cada requisição. O [Symfony] normalmente armazena o usuário logado em sua sessão (veja a seção sobre escopos), que é a solução mais simples para uma aplicação web. O estudo de caso, em todas as suas versões ([ASP.NET Core MVC], [Spring MVC], [NestJS], [Flask], [Laravel]), usa, em vez disso, um token (JWT, JSON Web Token), que usaremos aqui: após o login, o servidor gera um token contendo a identidade do usuário e o assina com uma chave secreta (é o princípio do cookie assinado do Exemplo 23). O token é armazenado em um cookie; o navegador o reenvia a cada requisição; o servidor verifica a assinatura. O usuário pode ler seu token, mas não pode modificá-lo: qualquer modificação invalida a assinatura. O formato é padronizado (RFC 7519), entendido por todas as linguagens de programação, e o token inclui sua data de expiração. Acima de tudo, o servidor não precisa armazenar nada: qualquer servidor que conheça a chave pode verificar o token.

    O [Symfony] tem um componente de segurança completo, integrado pelo SecurityBundle, cujos elementos usaremos como são:

    • as URLs da aplicação são distribuídas entre firewalls (firewalls), cada um com seu próprio método de autenticação dos usuários;
    • a autenticação é feita por authenticators (authenticators): objetos que determinam a identidade do usuário a cada requisição. O [Symfony] fornece vários deles (formulário de login, sessão, token de API etc.); escreveremos o nosso, que lê o token JWT. O restante da aplicação vê apenas o resultado: o usuário autenticado, fornecido por [#[CurrentUser]], [$this->getUser()] e, nas views, [app.user];
    • os usuários são fornecidos por um user provider, e suas senhas recebem hash do PasswordHasher (algoritmo [bcrypt]);
    • as autorizações são baseadas em papéis: a proteção de páginas é descrita por regras de controle de acesso ([access_control]) ou pelo atributo [#[IsGranted]] das ações; as views verificam um direito com [is_granted];
    • As tentativas de login são limitadas pelo componente RateLimiter (Exemplo 27).

    Tudo isso é feito por listeners de eventos do kernel (capítulo anterior): o firewall escuta [kernel.request] (prioridade 8), [#[IsGranted]] é lido em [kernel.controller_arguments], e as negações de acesso são exceções, tratadas em [kernel.exception].

    A geração e a verificação de tokens ficam a cargo da biblioteca [firebase/php-jwt], a mais usada em [PHP], instalada pelo arquivo [composer.json] dos exemplos. (Existe um bundle muito usado para tokens, o JWT e [LexikJWTAuthenticationBundle], projetado para APIs; para uma aplicação web, bastam algumas linhas, que ilustram melhor o mecanismo.)

    O token é assinado com uma chave secreta, que não deve ser escrita diretamente no código. É hora de separar de verdade a configuração do código.     O padrão exige que o algoritmo usado (HMAC-SHA256) tenha uma chave de pelo menos 256 bits, ou 32 bytes; a biblioteca rejeita qualquer chave mais curta. O código em si não lê diretamente o arquivo [.env]: o componente [Dotenv] (exemplo 01) o converteu em variáveis de ambiente, que o contêiner fornece aos serviços que as solicitam (veremos isso com o serviço [AuthService]). Uma variável de ambiente real tem precedência sobre o arquivo [.env]: no [Linux] ou no [macOS], a aplicação seria iniciada com uma chave diferente da seguinte forma:

    1
    JWT_SECRET="another-key-of-at-least-thirty-two-characters" php -d variables_order=EGPCS -S localhost:8000 -t public

    1
2
    $env:JWT_SECRET="another-key-of-at-least-thirty-two-characters"
php -d variables_order=EGPCS -S localhost:8000 -t public

    (A opção [-d variables_order=EGPCS] instrui o [PHP] a preencher o array [$_ENV] com as variáveis de ambiente, o que sua configuração padrão nem sempre faz.) Em produção, os segredos costumam ser confiados ao [Symfony] vault (secrets vault, comando [bin/console secrets:set]), que os armazena criptografados dentro do projeto.

// src/Security/UsersService.php: os usuários, em memória (o exemplo 28
// e o estudo de caso os colocarão em um banco de dados). UserProviderInterface: um
// PROVIDER de usuários, no sentido do Symfony (veja config/packages/security.yaml)

namespace App\Security;

use Symfony\Component\Security\Core\Exception\UnsupportedUserException;
use Symfony\Component\Security\Core\Exception\UserNotFoundException;
use Symfony\Component\Security\Core\User\UserInterface;
use Symfony\Component\Security\Core\User\UserProviderInterface;

class UsersService implements UserProviderInterface
{
    // NUNCA guardamos uma senha, apenas seu hash bcrypt, calculado
    // de uma vez por todas por: php -r "echo password_hash('marie', PASSWORD_BCRYPT);"
    private const USERS = [
        'marie' => ['Marie Pélissier', 'USER', '$2y$10$2DnOgGBiVcyc07su9rj2E.EvOoyPFzHN/h9PLKDuoW5P7UGtclW6W'],
        'admin' => ['Administrator', 'ADMIN', '$2y$10$m5o9euCi0EdgoZkLVw.UsO58RxJcqhMBfVrlLMCIOh2LyGSjuN29K'],
    ];

    public function find(string $login): ?User
    {
        if (! isset(self::USERS[$login])) {
            return null;
        }
        [$name, $role, $hash] = self::USERS[$login];
        return new User($login, $name, $role, $hash);
    }

    // os três métodos de UserProviderInterface
    public function loadUserByIdentifier(string $identifier): UserInterface
    {
        return $this->find($identifier) ?? throw new UserNotFoundException();
    }

    // o usuário armazenado na sessão, a recarregar: nunca chamado aqui,
    // já que o firewall é stateless
    public function refreshUser(UserInterface $user): UserInterface
    {
        throw new UnsupportedUserException();
    }

    public function supportsClass(string $class): bool
    {
        return $class === User::class;
    }
}
    • Linhas 17–20: dois usuários de teste, fixados no código (o exemplo 28 e o estudo de caso os armazenarão em um banco de dados): para cada login, o nome, o papel e o hash da senha. O hash é gerado com o algoritmo bcrypt, projetado para senhas. Ele tem duas características marcantes. É intencionalmente lento, com um nível de lentidão ajustável (o custo, aqui definido como 10: 2^10 ciclos de computação, o que resulta no hash [$10$]): algumas dezenas de milissegundos, imperceptíveis para um usuário, mas que tornam muito custoso para um invasor tentar bilhões de senhas. Ele usa salt: um salt gerado aleatoriamente é misturado à senha antes do hash e armazenado dentro do próprio hash (os 22 caracteres que seguem [$10$]); assim, dois usuários com a mesma senha terão hashes diferentes. Os hashes foram calculados uma única vez pela função [password_hash] do [PHP] (linha 16), ou pelo comando [bin/console security:hash-password] do [Symfony]: calculá-los a cada requisição seria uma perda de tempo desnecessária, já que a aplicação é reconstruída a cada requisição. O [bcrypt] considera apenas os primeiros 72 bytes de uma senha: o estudo de caso leva isso em conta;
    • linhas 22–29: o usuário de um login, ou [null]. [isset] verifica a existência de uma chave; a atribuição [[$name, $role, $hash] = ...] desestrutura um array: cada variável recebe o elemento correspondente;
    • linhas 32–47: os três métodos da interface [UserProviderInterface], que fazem da classe um provider de usuários: [loadUserByIdentifier] retorna o usuário associado a um identificador, ou lança a exceção [UserNotFoundException]; [refreshUser] recarrega o usuário armazenado na sessão (desnecessário com um firewall stateless); [supportsClass] especifica a classe dos usuários fornecidos. O operador [??] seguido de [throw] lança a exceção quando a expressão à esquerda é avaliada como [null].

    <?php
// src/Security/AuthService.php: a verificação das senhas e dos tokens JWT

namespace App\Security;

use Firebase\JWT\JWT;
use Firebase\JWT\Key;
use Symfony\Component\DependencyInjection\Attribute\Autowire;
use Symfony\Component\PasswordHasher\Hasher\UserPasswordHasherInterface;
use Throwable;

class AuthService
{
    // o nome do cookie que carrega o token
    public const COOKIE = 'token';

    public function __construct(
        private UsersService $users,
        // o serviço de hash de senhas (veja config/packages/security.yaml)
        private UserPasswordHasherInterface $hasher,
        // #[Autowire(env: ...)]: o valor de uma variável de ambiente (arquivo .env);
        // o prefixo int: o converte em inteiro
        #[Autowire(env: 'JWT_SECRET')] private string $secret,
        #[Autowire(env: 'int:JWT_DURATION_MINUTES')] public readonly int $durationMinutes,
    ) {
    }

    // o usuário, ou null se o login for desconhecido ou a senha estiver errada.
    // isPasswordValid calcula o hash da senha digitada com o salt do hash armazenado e
    // depois compara os dois resultados
    public function validate(?string $login, ?string $password): ?User
    {
        if (! $login || $password === null) {
            return null;
        }
        $user = $this->users->find($login);
        if ($user === null || ! $this->hasher->isPasswordValid($user, $password)) {
            return null;
        }
        return $user;
    }

    // o token JWT do usuário, assinado com a chave secreta (HMAC-SHA256)
    public function createToken(User $user): string
    {
        $now = time();
        // o conteúdo do token: as "claims" (declarações sobre o usuário)
        $claims = [
            'sub' => $user->login,
            'name' => $user->name,
            'role' => $user->role,
            'iat' => $now,
            'exp' => $now + $this->durationMinutes * 60,
        ];
        return JWT::encode($claims, $this->secret, 'HS256');
    }

    // o usuário descrito por um token cuja assinatura e data de expiração
    // são válidas; null caso contrário (token forjado, expirado ou ilegível)
    public function check(string $token): ?User
    {
        try {
            // decode retorna um objeto; (array) o converte em array associativo
            $claims = (array) JWT::decode($token, new Key($this->secret, 'HS256'));
        } catch (Throwable) {
            return null;
        }
        return new User($claims['sub'], $claims['name'], $claims['role'], claims: $claims);
    }
}
    • Linhas 17–26: o serviço recebe o provider de usuários, o serviço de hash de senhas ([UserPasswordHasherInterface], que aplica o algoritmo selecionado em [security.yaml]) e dois valores de configuração. O atributo [#[Autowire(env: 'NAME')]] fornece o valor de uma variável de ambiente; um prefixo a converte: [int:] para um inteiro (há outros: [bool:], [json:], [base64:]...). O tempo de vida é uma propriedade pública somente leitura: o controller a utilizará;
    • linhas 31–41: verificação de um nome de usuário e de uma senha. [isPasswordValid] calcula o hash da senha digitada usando o salt do hash armazenado e compara os dois hashes. Um nome de usuário desconhecido e uma senha incorreta produzem o mesmo resultado, [null];
    • Linhas 44–56: geração do token. O token contém um array de declarações (claims) sobre o usuário. Algumas têm nomes padronizados: [sub] (subject), o identificador do usuário; [iat] (issued at), a data de criação; [exp] (expiration), a data de expiração. As datas são expressas em segundos decorridos desde 1º de janeiro de 1970 (a função [time()] do [PHP]). Os demais campos são opcionais: aqui, o nome e o papel. [JWT::encode] gera o token e o assina usando o algoritmo [HS256] (HMAC-SHA256, uma assinatura com chave secreta compartilhada);
    • linhas 60–69: verificação do token. [JWT::decode] verifica a assinatura e a data de expiração e, em seguida, retorna as declarações (um objeto, convertido em array por [(array)]). Qualquer anomalia (token forjado, expirado ou malformado) lança uma exceção; [catch (Throwable)] captura todas ([Throwable] é a interface de todas as exceções e erros do [PHP]; o nome da variável é opcional quando ela não é usada). O objeto [Key] associa a chave a um algoritmo: um token que especifique um algoritmo diferente (ou nenhum, [none]) seria rejeitado. O token válido se torna um [User], sem hash, junto com suas declarações (parâmetro chamado [claims]).

// src/Security/TokenAuthenticator.php: o AUTHENTICATOR do firewall (veja
// config/packages/security.yaml): a cada requisição, ele estabelece quem é o usuário,
// a partir do token JWT do cookie [token]

namespace App\Security;

use Symfony\Component\HttpFoundation\RedirectResponse;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Security\Core\Authentication\Token\TokenInterface;
use Symfony\Component\Security\Core\Exception\AuthenticationException;
use Symfony\Component\Security\Core\Exception\CustomUserMessageAuthenticationException;
use Symfony\Component\Security\Http\Authenticator\AbstractAuthenticator;
use Symfony\Component\Security\Http\Authenticator\Passport\Badge\UserBadge;
use Symfony\Component\Security\Http\Authenticator\Passport\Passport;
use Symfony\Component\Security\Http\Authenticator\Passport\SelfValidatingPassport;
use Symfony\Component\Security\Http\EntryPoint\AuthenticationEntryPointInterface;

class TokenAuthenticator extends AbstractAuthenticator implements AuthenticationEntryPointInterface
{
    public function __construct(private AuthService $auth)
    {
    }

    // o authenticator age apenas se a requisição carregar o cookie do token;
    // caso contrário, o visitante permanece anônimo
    public function supports(Request $request): ?bool
    {
        return $request->cookies->has(AuthService::COOKIE);
    }

    // o PASSPORT do usuário: quem ele é (o badge) e como verificá-lo.
    // O token já foi verificado: o passport se valida sozinho (SelfValidatingPassport)
    public function authenticate(Request $request): Passport
    {
        $user = $this->auth->check($request->cookies->get(AuthService::COOKIE));
        if ($user === null) {
            throw new CustomUserMessageAuthenticationException('invalid token');
        }
        // o badge: o login e uma função que retorna o usuário (aqui, o do
        // token, sem consultar a lista de usuários)
        return new SelfValidatingPassport(new UserBadge($user->login, fn () => $user));
    }

    // um token válido: null, a requisição segue seu caminho até a action
    public function onAuthenticationSuccess(Request $request, TokenInterface $token, string $firewallName): ?Response
    {
        return null;
    }

    // um token inválido (expirado, forjado): vá para /login, e apagamos o cookie
    public function onAuthenticationFailure(Request $request, AuthenticationException $exception): ?Response
    {
        $response = new RedirectResponse('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }

    // o ENTRY POINT: a resposta dada a um visitante anônimo que solicita uma
    // página protegida; aqui, um redirecionamento para a página de login
    public function start(Request $request, ?AuthenticationException $authException = null): Response
    {
        return new RedirectResponse('/login');
    }
}

    Para cada requisição que passa pelo firewall, o [Symfony] chama os métodos do autenticador nesta ordem:

    • linhas 28–31: [supports]: o autenticador está envolvido nesta requisição? Sim, se ela contiver o cookie do token. Caso contrário, nada acontece: o visitante permanece anônimo;
    • linhas 35–44: [authenticate] constrói um passaporte: a identidade do usuário (um badge, [UserBadge]) e as credenciais a verificar. Um formulário de login padrão incluiria a senha digitada no passaporte, que o [Symfony] verificaria por conta própria. Aqui, a prova é o token, já verificado pelo [AuthService]: o passaporte se valida sozinho ([SelfValidatingPassport]). O badge contém o login e uma função que identifica o usuário: neste caso, o usuário descrito pelo token, sem consultar a lista de usuários (sem essa função, o [Symfony] solicitaria o usuário ao provider). Um token inválido lança uma exceção de autenticação;
    • linhas 47–50: [onAuthenticationSuccess]: a autenticação foi bem-sucedida. Retornar [null] permite que a requisição prossiga até a ação com um usuário autenticado. (Um formulário de login redirecionaria aqui para a página inicial);
    • linhas 53–58: [onAuthenticationFailure]: a autenticação falhou (token expirado ou forjado). A resposta redireciona para a página de login e aproveita para limpar o cookie: [clearCookie] adiciona à resposta um cookie vazio e já expirado;
    • linhas 62–65: [start] é o método da interface [AuthenticationEntryPointInterface]: o ponto de entrada do firewall, ou seja, a resposta enviada a um visitante anônimo que solicita uma página protegida. Neste caso, um redirecionamento para a página de login.

    O autenticador não nega o acesso: ele determina quem é o usuário, ou determina que o usuário é anônimo. Isso é autenticação. As negações são responsabilidade do controle de acesso.

namespace App\Controller;

use App\Security\AuthService;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\Routing\Attribute\Route;

class AuthController extends AbstractController
{
    public function __construct(private AuthService $auth)
    {
    }

    #[Route('/', methods: ['GET'])]
    public function home(): Response
    {
        return $this->redirect('/profile');
    }

    #[Route('/login', methods: ['GET'])]
    public function form(): Response
    {
        return $this->render('auth/login.html.twig');
    }

    #[Route('/login', methods: ['POST'])]
    public function login(Request $request): Response
    {
        // o token anti-CSRF do formulário (veja o exemplo 21)
        if (! $this->isCsrfTokenValid('login', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $login = $request->getPayload()->getString('login');
        $user = $this->auth->validate($login, $request->getPayload()->getString('password'));
        if ($user === null) {
            // uma mensagem deliberadamente vaga: não dizemos se é o login ou a senha
            return $this->render('auth/login.html.twig', ['login' => $login,
                'error' => 'Incorrect login or password.']);
        }
        // o token, em um cookie: o JavaScript da página não consegue lê-lo
        // (httpOnly); ele não acompanha as requisições POST vindas de outros sites
        // (sameSite); ele desaparece ao mesmo tempo em que o token expira
        $response = $this->redirect('/profile');
        $response->headers->setCookie(Cookie::create(AuthService::COOKIE, $this->auth->createToken($user))
            ->withExpires(time() + $this->auth->durationMinutes * 60)
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $response;
    }

    // logout: apenas POST (um simples link, colocado em outro site, não pode
    // desconectar o usuário sem que ele saiba); apagamos o cookie
    #[Route('/logout', methods: ['POST'])]
    public function logout(Request $request): Response
    {
        if (! $this->isCsrfTokenValid('logout', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $response = $this->redirect('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }
}
    • linhas 36–38: o formulário de login é protegido contra requisições forjadas, como todos os formulários (exemplo 21);
    • linhas 40–45: o processo de login. Se ele falhar, o formulário é exibido novamente com o nome de usuário digitado e uma mensagem deliberadamente vaga: dizer “nome de usuário desconhecido” revelaria a um invasor quais nomes de usuário existem;
    • Linhas 49–54: se houver sucesso, o token é armazenado em um cookie e o usuário é redirecionado para a página protegida (esquema PRG). O cookie é [httpOnly]: o [JavaScript] da página não pode lê-lo, o que protege o token contra a injeção de scripts (XSS); ele é [SameSite=Lax]: o navegador não o envia com uma requisição POST originada em outro site, o que protege a aplicação contra ataques CSRF; sua data de expiração ([withExpires], aqui um número de segundos desde 1970) é a mesma do token. Em produção, com HTTPS, acrescentaríamos [withSecure(true)]: o cookie nunca seria enviado por uma conexão não criptografada;
    • Linhas 59–68: o logout exclui o cookie ([clearCookie]). Essa é uma ação POST, protegida por um token anti-CSRF: um simples link para [/logout], colocado em outro site ou dentro de uma imagem, não pode desconectar o usuário sem que ele saiba. Observe uma limitação dos tokens: o próprio token continua válido até expirar. Quem tiver feito uma cópia dele ainda poderia usá-lo. É por isso que seu tempo de vida é limitado.

        // levemente movido ao acaso
        $step = ($l - 20) / strlen($text);
        foreach (str_split($text) as $i => $character) {
            $scale = self::random(4.6, 5.6);    // tamanho de uma unidade da grade, em pixels
            $angle = self::random(-0.35, 0.35);   // rotação, em radianos (cerca de ±20°)
            $cx = 10 + $step * ($i + 0.5) + self::random(-3, 3);    // centro do caractere

                    $x = ($stroke[$k] - 2 + self::random(-0.2, 0.2)) * $scale;
                    $y = ($stroke[$k + 1] - 3 + self::random(-0.2, 0.2)) * $scale;

                    $d[] = sprintf('%s%.1f %.1f', $k === 0 ? 'M' : 'L', $px, $py);

// src/Security/CaptchaService.php: os CAPTCHAs pendentes, mantidos pelo servidor,
// no cache (veja o exemplo 20)

namespace App\Security;

use Psr\Cache\CacheItemPoolInterface;

class CaptchaService
{
    // o tempo de vida de um CAPTCHA, em segundos
    private const LIFETIME = 600;

    public function __construct(private CacheItemPoolInterface $cache)
    {
    }

    public function generate(): Captcha
    {
        $text = CaptchaDrawing::randomText(5);
        // um identificador aleatório, impossível de adivinhar: 12 bytes sorteados por um
        // gerador criptográfico (random_bytes), escritos em hexadecimal (bin2hex)
        $id = bin2hex(random_bytes(12));
        // a resposta esperada, no cache, por 10 minutos (expiresAfter): o
        // cache a esquecerá sozinho depois
        $item = $this->cache->getItem("captcha.$id");
        $this->cache->save($item->set($text)->expiresAfter(self::LIFETIME));
        return new Captcha($id, CaptchaDrawing::svg($text));
    }

    // o CAPTCHA é CONSUMIDO em todos os casos: uma imagem é usada uma única vez
    public function check(?string $id, ?string $answer): bool
    {
        // um identificador malformado não pode ser uma chave do cache
        if ($id === null || ! ctype_xdigit($id) || $answer === null) {
            return false;
        }
        $item = $this->cache->getItem("captcha.$id");
        // deleteItem: a resposta é removida do cache, esteja certa ou não
        $this->cache->deleteItem("captcha.$id");
        if (! $item->isHit()) {
            return false;    // identificador desconhecido, ou CAPTCHA expirado
        }
        // strcasecmp retorna 0 para duas strings iguais, sem diferenciar maiúsculas de minúsculas
        return strcasecmp($item->get(), trim($answer)) === 0;
    }
}
    • Linhas 18–29: um novo CAPTCHA: um texto aleatório, um identificador aleatório e impossível de adivinhar, e a imagem. Para cada identificador, o servidor armazena a resposta esperada no cache (exemplo 20) por dez minutos: o método [expiresAfter] do item de cache define seu tempo de vida em segundos. Passado esse tempo, o cache o descarta automaticamente. A página recebe apenas o identificador e a imagem: a resposta nunca sai do servidor;
    • linhas 32–46: a validação. O identificador vem do cliente: primeiro verificamos que ele é composto por dígitos hexadecimais ([ctype_xdigit]), já que certos caracteres ([{}()/\@:]) são proibidos em chaves de cache, o que lançaria uma exceção. O item é lido e depois removido do cache ([deleteItem]): o CAPTCHA é consumido em todos os casos, com sucesso ou não. Sem isso, um programa poderia tentar todas as respostas possíveis na mesma imagem. A comparação ignora maiúsculas e minúsculas ([strcasecmp] retorna 0 para duas strings iguais, independentemente de letras maiúsculas ou minúsculas) e os espaços ao redor da entrada ([trim]).

namespace App\Controller;

use App\Security\AuthService;
use App\Security\CaptchaService;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Cookie;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\RateLimiter\RateLimiterFactoryInterface;
use Symfony\Component\Routing\Attribute\Route;

class AuthController extends AbstractController
{
    // $loginLimiter: a factory do limiter [login] (veja config/packages/framework.yaml);
    // o nome do parâmetro designa o limiter
    public function __construct(
        private AuthService $auth,
        private CaptchaService $captchas,
        private RateLimiterFactoryInterface $loginLimiter,
    ) {
    }

    #[Route('/', methods: ['GET'])]
    public function home(): Response
    {
        return $this->redirect('/profile');
    }

    #[Route('/login', methods: ['GET'])]
    public function form(): Response
    {
        return $this->loginPage();
    }

    #[Route('/login', methods: ['POST'])]
    public function login(Request $request): Response
    {
        $inputs = $request->getPayload();
        if (! $this->isCsrfTokenValid('login', $inputs->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $login = $inputs->getString('login');
        // o limiter DESTE cliente: a chave de seu contador de falhas é seu endereço IP
        $limiter = $this->loginLimiter->create($request->getClientIp());

        // 1. um endereço bloqueado nem chega a ser atendido; consume(0) consulta o
        // contador sem consumir nada
        $state = $limiter->consume(0);
        if ($state->getRemainingTokens() === 0) {
            $seconds = $state->getRetryAfter()->getTimestamp() - time();
            return $this->loginPage($login, "Too many attempts: try again in $seconds s.");
        }
        // 2. primeiro o CAPTCHA (barato), depois a senha (bcrypt, caro);
        // consume(): mais uma falha
        if (! $this->captchas->check($inputs->getString('captchaId'), $inputs->getString('captcha'))) {
            $limiter->consume();
            return $this->loginPage($login, 'The image code is incorrect.');
        }
        $user = $this->auth->validate($login, $inputs->getString('password'));
        if ($user === null) {
            $limiter->consume();
            return $this->loginPage($login, 'Incorrect login or password.');
        }
        // um login bem-sucedido apaga as falhas
        $limiter->reset();
        $response = $this->redirect('/profile');
        $response->headers->setCookie(Cookie::create(AuthService::COOKIE, $this->auth->createToken($user))
            ->withExpires(time() + $this->auth->durationMinutes * 60)
            ->withHttpOnly(true)
            ->withSameSite(Cookie::SAMESITE_LAX));
        return $response;
    }

    #[Route('/logout', methods: ['POST'])]
    public function logout(Request $request): Response
    {
        if (! $this->isCsrfTokenValid('logout', $request->getPayload()->getString('_csrf_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $response = $this->redirect('/login');
        $response->headers->clearCookie(AuthService::COOKIE);
        return $response;
    }

    // cada exibição do formulário constrói um NOVO CAPTCHA
    private function loginPage(?string $login = null, ?string $error = null): Response
    {
        return $this->render('auth/login.html.twig', ['login' => $login, 'error' => $error,
            'captcha' => $this->captchas->generate()]);
    }
}
    • linhas 21–26: o controller recebe a fábrica do limitador [login];
    • linha 49: o limitador deste cliente, [create(key)], retorna um limitador que tem seu próprio contador sob essa chave — neste caso, o endereço IP do cliente ([getClientIp()]);
    • linhas 53–57: um endereço bloqueado nem sequer é ouvido. [consume(0)] consulta o limitador sem consumir nada; o objeto [RateLimit] que ele retorna fornece o número de tokens restantes ([getRemainingTokens()]) e a data em que a ação voltará a ser permitida ([getRetryAfter()]), da qual podemos deduzir o número de segundos de espera;
    • Linhas 60–68: o CAPTCHA é verificado antes da senha; verificá-lo custa quase nada, ao passo que o [bcrypt] é intencionalmente lento. Um programa que digite o CAPTCHA errado, portanto, não acionaria o [bcrypt]. Cada falha — seja do CAPTCHA ou da senha — consome um token ([consume()], que consome um por padrão). Após a terceira falha, não restam tokens: o endereço fica bloqueado até o fim da janela de 60 segundos, contada a partir da primeira falha;
    • linha 70: um login bem-sucedido zera as tentativas malsucedidas ([reset()]);
    • linhas 91–95: a cada exibição do formulário, um novo CAPTCHA é gerado, mesmo após uma tentativa malsucedida.

    O SecurityBundle também oferece um limite de conexão integrado (a opção de firewall [login_throttling] ), que se aplica aos seus próprios autenticadores de login ([form_login]...), e não à nossa ação. Para limitar o número de requisições a uma rota, usaríamos um limitador da mesma maneira, seja dentro da ação, seja em um listener de [kernel.request]. Optamos por contar apenas as tentativas malsucedidas, para não incomodar um usuário que faz login normalmente.
