    Este documento é um produto da IA Claude, da Anthropic. Ele dá seguimento ao documento “Introdução passo a passo ao framework web [Laravel]” (2026), que por sua vez deu seguimento aos documentos “Introdução passo a passo ao framework web [Flask],” "Introdução passo a passo ao framework web [Spring MVC]," "Introdução passo a passo ao framework web [ASP.NET Core MVC]" e "Introdução passo a passo ao framework web [NestJS]" (2026). Este documento permanece no universo [PHP], mas muda de framework:

    • o framework [Laravel] é substituído pelo framework [Symfony] 8.1, ainda com a linguagem [PHP] (versão 8.4 ou posterior);
    • as views [Blade] são substituídas por views [Twig], a engine de views do [Symfony];
    • a validação por meio das regras do [Laravel] e das requisições de formulário ([FormRequest]) é substituída pelo componente Validator do [Symfony] (restrições, escritas como atributos [PHP]) e por seu componente Form, que descreve os formulários por meio de classes;
    • os guards, os middlewares e os componentes [Gate] do [Laravel] são substituídos pelo componente Security do [Symfony]: firewalls, autenticadores, papéis, hash de senhas e um limitador de tentativas, complementado pela biblioteca [firebase/php-jwt] para tokens JWT;
    • Os middlewares, no entanto, não existem no [Symfony]: event listeners são usados para intervir no processamento da requisição;
    • o ORM [Eloquent] é substituído pelo [Doctrine], o ORM associado ao [Symfony], que por sua vez trabalha com o banco [MySQL].

    O documento segue de perto a estrutura do curso de [Laravel]: primeiro, vários pequenos projetos, cada um centrado em um único conceito, seguidos de um estudo de caso completo — uma aplicação web de agendamento de consultas em um consultório médico — com todos os arquivos integralmente comentados. Os exemplos têm os mesmos números e abordam os mesmos temas que nos cursos de [Laravel], [Flask], [Spring MVC], e [ASP.NET Core MVC]: um leitor que conheça um desses cursos pode comparar os frameworks caso a caso. No entanto, isso não é necessário: este documento é autossuficiente e não pressupõe nenhum conhecimento prévio desses frameworks. Os únicos pré-requisitos são noções básicas de programação web (o protocolo HTTP, a linguagem HTML) e os fundamentos da linguagem [PHP] (variáveis, arrays, funções, classes). O curso “Introdução à linguagem PHP7 por meio de exemplos” (2019) apresenta a própria linguagem para quem precisa aprendê-la primeiro; os recursos novos do [PHP] 8 usados aqui (propriedades promovidas, classes [readonly], atributos, enumerações, argumentos nomeados, operador null-safe etc.) são explicados quando aparecem pela primeira vez.

    1.1. O papel do Symfony em uma aplicação web

    Uma aplicação web costuma ser construída em camadas, e cada camada se comunica apenas com as camadas vizinhas:

    • a camada web recebe as requisições HTTP do navegador e devolve a ele páginas HTML. É a camada que o [Symfony] nos ajuda a escrever;
    • a camada de negócio contém as regras de negócio da aplicação (por exemplo, “um paciente só pode ter uma consulta futura”). Ela não sabe nada sobre a web: poderia igualmente atender a uma aplicação de linha de comando;
    • a camada de acesso a dados (camada DAO, de Data Access Object) lê e grava no banco de dados. Usaremos o [Doctrine], o ORM (Object Relational Mapper) associado ao [Symfony], que mapeia linhas de tabelas em objetos [PHP].

    A própria camada web segue o padrão MVC (Model-View-Controller):

    • o controller (C) é uma classe [PHP] cujos métodos, chamados de actions, tratam cada um um tipo específico de requisição (por exemplo, [GET /schedule]). Uma action lê os parâmetros da requisição, processa-a por meio da camada de negócio e, em seguida, escolhe a view a exibir;
    • o modelo (M) é o conjunto de dados que a action passa à view;
    • a view (V) é um arquivo [Twig] (extensão [.html.twig]): uma página HTML que contém expressões [{{ ... }}] e instruções [{% if %}], [{% for %}]... que o motor [Twig] substitui pelos dados do modelo.

    Uma observação sobre a terminologia, para evitar confusão: no [Symfony], as classes que representam tabelas do banco de dados são chamadas de entidades (pasta [src/Entity]). Neste documento, o termo “modelo” sempre se referirá, portanto, ao modelo da view (os dados passados a uma view) ou, no Capítulo 2, ao modelo da action (os dados que ela recebe). O termo “template” designa a view comum da qual as outras páginas herdam (capítulo sobre views).

    O processamento de uma requisição segue as etapas numeradas do diagrama:

    • 1: O navegador envia uma requisição HTTP, como [GET /schedule?doctorId=1&day=2026-09-26];
    • 2: O servidor web recebe a requisição e a repassa à aplicação [Symfony] por meio do arquivo [public/index.php]. Durante o desenvolvimento, esse servidor é o que acompanha o [PHP], iniciado pelo comando [php -S localhost:8000 -t public]; em produção, será um servidor como o [nginx] ou o [Apache], associado ao [PHP-FPM]. O arquivo [public/index.php] repassa a requisição ao núcleo (kernel) da aplicação, que a faz passar por uma série de eventos: participam classes do [Symfony] e da aplicação, bem como listeners (sessão, segurança, idioma etc.). Um deles compara o caminho solicitado com as rotas da aplicação e seleciona a action responsável por essa requisição: é o roteamento;
    • 3: A action solicita à camada de negócio os dados de que precisa; se necessário, a camada de negócio recorre à camada DAO, que consulta o banco de dados [MySQL] em SQL;
    • 4: A action constrói o modelo M da view e instrui o motor [Twig] a gerar a página (método [render]);
    • 5: A página HTML gerada pela view é a resposta da action, que o [Symfony] devolve ao navegador.

    O [Symfony] é, junto com o [Laravel], um dos dois grandes frameworks web do mundo [PHP]. Gratuito e de código aberto, criado em 2005 por Fabien Potencier (e pela empresa francesa SensioLabs), funciona em qualquer lugar em que funcione o [PHP] ([Windows], [Linux], [macOS]), e o [PHP] funciona em quase todas as hospedagens web. [Symfony] é antes de tudo uma coleção de cerca de cinquenta componentes — bibliotecas independentes (requisições e respostas HTTP, roteamento, console, formulários, validação, segurança etc.) — tão bem conceituados que outros projetos os utilizam: o [Laravel] próprio é construído sobre vários deles, e os leitores do curso anterior já os encontraram. O framework [Symfony] reúne esses componentes por meio de bundles (pacotes de integração) e de um contêiner de serviços que cria os objetos da aplicação. Em comparação com o [Laravel], o [Symfony] faz escolhas claras: nada de facades nem de funções globais, mas serviços obtidos por injeção de dependência; configuração explícita em arquivos YAML; atributos [PHP] ([#[Route]], [#[Assert\NotBlank]]...) para descrever o código; e um ORM, o [Doctrine], que separa os objetos de sua persistência. É um framework renomado por seu rigor, sua documentação e sua política de versionamento: uma versão menor a cada seis meses, uma versão de “suporte de longo prazo” a cada dois anos e a garantia de que uma aplicação sem avisos de obsolescência passará para a próxima versão principal sem modificações. [Symfony] pode criar servidores que devolvem JSON a um cliente [JavaScript] ([Angular], [React], [Vue.js], [Flutter]...), assim como aplicações web tradicionais, em que o servidor gera as páginas HTML e o navegador se limita a exibi-las. É esse segundo caso de uso que este documento examina.

    Uma particularidade do [PHP] explica muito do [Symfony]: a aplicação é reconstruída a cada requisição e depois descartada (exemplo 01). [Symfony] compensa esse custo compilando sua configuração de uma vez por todas em código [PHP], que é armazenado em um cache (pasta [var/cache]). Voltaremos a isso com frequência.

    1.2. Ferramentas utilizadas

    Os exemplos foram escritos e testados com as seguintes ferramentas (sua instalação é descrita no apêndice):

    • [PHP] 8.4 (qualquer versão 8.4 ou posterior serve), com as extensões [intl], [mbstring], [openssl], e [pdo_mysql];
    • [Composer] 2, o gerenciador de bibliotecas do [PHP];
    • o editor [Visual Studio Code], com as extensões [PHP Intelephense] (análise de código), [Twig Language 2] (views) e [YAML] (arquivos de configuração);
    • um navegador moderno ([Chrome], [Firefox], [Edge]);
    • a ferramenta de linha de comando [curl], que exibe as respostas HTTP brutas (ela acompanha o [Windows] 10 e 11);
    • um SGBD, [MySQL] (ou [MariaDB]), por exemplo, o do [Laragon] no [Windows], a partir do capítulo sobre acesso a dados e para o estudo de caso. No [Windows], o [Laragon] instala o [PHP], o [Composer] e o [MySQL] de uma só vez.

    O [Symfony] e as demais bibliotecas não fazem parte do [PHP]: [Composer] as baixa do repositório [Packagist] durante a instalação (portanto, é preciso estar conectado à Internet nesse dia) e as coloca em uma pasta [vendor]. Cada projeto descreve suas bibliotecas em um arquivo [composer.json]. A tabela a seguir lista as principais, com as versões utilizadas:

    O [Symfony] normalmente é instalado criando-se um projeto completo com o comando:

    1
    composer create-project symfony/skeleton my-project

    ou com a ferramenta de linha de comando do [Symfony] (o programa [symfony]; veja os apêndices): [symfony new my-project --webapp]. [Composer] baixa então o esqueleto de uma aplicação [Symfony] e, em seguida, suas bibliotecas. O esqueleto também contém o [Symfony Flex], um plugin do [Composer] que, a cada vez que uma biblioteca ([composer require twig]) é instalada, escreve seus próprios arquivos de configuração a partir de templates publicados on-line. É assim que se inicia um projeto real. Para o aprendizado, esse método tem um inconveniente: os arquivos aparecem sozinhos, sem que se saiba para que servem. Os exemplos deste documento partem, portanto, da outra extremidade: o Exemplo 01 é a menor aplicação [Symfony] possível, e cada exemplo acrescenta apenas os arquivos de que precisa, escritos e comentados à mão. O estudo de caso final segue a estrutura de uma aplicação [Symfony] padrão.

    O estudo de caso requer um SGBD, o MySQL, um interpretador PHP e o instalador de pacotes PHP [composer]. O Laragon pode fornecer tudo isso e muito mais. Em setembro de 2026, o Laragon está disponível na URL [Download Laragon – Fast & Modern Dev Environment ]. O Laragon vem com ferramentas que permitem instalar um servidor PHP e o SGBD [MySQL]:

    • em [1], um servidor web Apache;
    • em [2], o SGBD [MySQL];
    • em [3], uma ferramenta de mensagens que não usaremos;
    • [4] inicia todos os serviços (Apache, [MySQL], MailPit);
    • [5] exibe a página web da URL [http://localhost]. Por padrão, essa URL corresponde à pasta <laragon-install>\www, em que <laragon-install> é a pasta de instalação do Laragon;
    • em [6], inicia a ferramenta HeidiSQL, que permite gerenciar bancos de dados MySQL. Usaremos essa ferramenta para criar o banco de dados do estudo de caso;
    • em [7], abre um terminal; todos os binários necessários ao Laragon estão no PATH;
    • em [8], abre uma janela do Windows Explorer na pasta associada à URL [http://localhost];

    A pasta de instalação do Laragon contém os seguintes itens:

    • em [4], um gerenciador de bancos de dados;

    O banco de dados [dbrdvmedecins] foi criado. Eis o seu conteúdo:

    • em [1-3], a tabela [clients];
      • [id] é a chave primária da tabela;
      • [version] é o número de versão da linha. Esse número é incrementado a cada modificação da linha;
      • [titre, nom, prenom] identificam a pessoa;

    • em [1-3], a tabela [medecins];
      • [id] é a chave primária da tabela;
      • [version] é o número de versão da linha;
      • [titre, nom, prenom] identificam a pessoa;

    • Em [1-3], a tabela dos horários de consulta dos médicos:
      • [id]: chave primária;
      • [version]: número de versão da linha;
      • [id-medecin]: chave estrangeira que referencia a chave primária do médico;
      • [hdebut, mdebut]: hora e minutos do início da consulta. Assim, [8,20] significa 8h20.
      • [hfin, mfin]: hora e minutos do fim da consulta.

    • Em [1-3], a tabela [rv] das consultas agendadas;
      • [id]: chave primária;
      • [version]: número de versão;
      • [jour]: data da consulta;
      • [id_creneau]: chave estrangeira que referencia a chave primária do horário de consulta. Como um horário está ligado a um médico, sabemos qual médico atenderá essa consulta;
      • [id_client]: chave estrangeira para o número (chave primária) do paciente que comparece à consulta;

    • em [1-3], a tabela [users] lista os usuários autorizados a usar a aplicação RdvMedecins;
      • [id, version]: chave primária, número de versão;
      • [login, password]: credenciais do usuário;
      • [nom]: nome do usuário;
      • [role]: o papel do usuário. [ADMIN] tem todos os direitos de acesso. [USER] tem acesso somente de leitura. Esse usuário pode consultar a agenda de um médico, mas não pode marcar nem cancelar uma consulta;

    1.3.2. Executando o estudo de caso

    Nota do revisor: aconselho o leitor a executar o estudo de caso imediatamente, como descrito a seguir. Depois de compreender bem a finalidade dessa aplicação de agendamento de consultas, peça à sua IA favorita que modifique a aplicação da seguinte forma: a partir de agora, cada médico poderá:

    • definir seus próprios horários de consulta entre duas datas. Isso lhe permitirá ajustar a agenda conforme a necessidade;
    • retirar certos horários da agenda em um determinado dia — por exemplo, se estiver indisponível por motivos pessoais;

    A modificação não é trivial, pois envolve uma mudança na estrutura do banco de dados. Peça à IA que lhe forneça o novo código da aplicação e o script SQL para criar o novo banco de dados. Para isso, será preciso entregar a ela o arquivo ZIP com o projeto completo, bem como o script SQL do banco de dados antigo.

    1

    1
    [Sun Sep 27 18:40:12 2026] PHP 8.4.21 Development Server (http://localhost:8081) started

    O servidor de desenvolvimento escuta na porta 8081 da máquina ([localhost]). Cada requisição recebida será registrada no console, junto com as mensagens do [Symfony] (a rota selecionada, os comandos SQL enviados ao banco de dados);

    • Abra o endereço [http://localhost:8081] em um navegador:

    • Faça login com uma das contas de demonstração, cuja senha é igual ao nome de usuário: [admin] (administrador), [pelissier], [tatou], [dupont] (médicos), [martin], [durand], [bistrou], [german] (pacientes). Também é preciso digitar os caracteres da imagem, em maiúsculas ou minúsculas.

    Uma aplicação [PHP] não lê o banco de dados na inicialização: um erro de conexão só aparece na primeira página que consulta o banco, ou seja, no momento da conexão. O [Symfony] exibe então sua página de erro detalhada e registra o erro no console do servidor. Se a mensagem for [SQLSTATE[HY000] [2002] Connection refused], significa que o [MySQL] não foi iniciado; com [[1045] Access denied for user 'root'@'localhost'], significa que a senha está incorreta; com [[1049] Unknown database 'dbrdvmedecins2'], significa que o script SQL não foi executado; com [could not find driver], que a extensão [pdo_mysql] do [PHP] não está habilitada. Se a página exibir [Failed opening required '.../vendor/autoload_runtime.php'], significa que o [composer install] não foi executado; se o comando [php -S] falhar com a mensagem [Failed to listen on localhost:8081 (reason: Address already in use)], significa que a porta 8081 já está em uso (por outra versão da aplicação, por exemplo). O arquivo [README.md] da aplicação descreve outros cenários. Pare a aplicação com [Ctrl-C] no terminal.

    Para executar os exemplos, instale primeiro suas bibliotecas — uma vez por todas — em uma janela de terminal aberta na pasta [examples]:

    1
    composer install

    O [Composer] cria a pasta [examples/vendor], compartilhada por todos os 28 exemplos, e o arquivo [composer.lock], que registra as versões exatas instaladas (veja o estudo de caso). A pasta [common] contém o framework CSS [Bootstrap] ([common/bootstrap]) — compartilhado pelos exemplos que formatam suas páginas (a partir do Exemplo 15) — e o controller que o serve ([common/BootstrapController.php]; veja o Exemplo 15).

    Para executar um exemplo, abra um terminal em sua pasta (no [Visual Studio Code]: clique com o botão direito na pasta do exemplo e selecione “Open in Integrated Terminal”) e digite:

    1
    php -S localhost:8000 -t public

    Todos os exemplos escutam na porta 8000: só é possível executar um de cada vez (ou é preciso mudar a porta: [php -S localhost:8001 -t public]). Pare o servidor com [Ctrl-C] no terminal. Não é necessário reiniciar o servidor após modificar um arquivo [PHP], uma view ou a configuração: as alterações passam a valer na requisição seguinte (exemplo 01).

    Quando você abre a pasta [examples] no [Visual Studio Code], a extensão [PHP Intelephense] analisa todos os arquivos, inclusive os do [Symfony] na pasta [vendor]: em cada arquivo, você aproveita o preenchimento automático de código, a navegação até a definição de uma classe ou método (tecla [F12]) e a indicação de erros. Como todos os exemplos têm suas classes no namespace [App], a extensão pode sinalizar classes “duplicadas”: isso não tem efeito na execução, pois cada exemplo é executado de forma independente. Para evitar esses avisos, basta abrir a própria pasta do exemplo.
